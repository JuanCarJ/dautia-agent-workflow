# Codex Workflow Packaging Review

Find the smallest evidence-backed reusable asset, including the decision to create none. Review roughly the last 30 days, or all available history when shorter. Package the workflow, not the underlying product change.

Use recent thread timestamps and relevant turns as primary evidence; a title alone is not an occurrence. Then consult `MEMORY.md` and linked rollout summaries, treating remembered commands and external state as possibly stale. Use Chronicle only when enabled and verified to discover work outside Codex, and confirm material facts with the relevant repo, app, connector, host or provider. Inspect installed personal/plugin skills, custom agents and automations before creating anything. When local Codex assets are available, run `scripts/inventory-local-assets.sh` and supplement it with app thread and automation tools; that script does not inventory remote/plugin capabilities.

For each candidate, establish trigger, repeatable procedure, output or stop condition, dates and distinct executions, cost/risk/context, and existing coverage. Count distinct sessions or real executions rather than repeated messages in one incident. A single occurrence qualifies only when recurrence is clearly likely and costly. Reject unstable, ambiguous or sensitive procedures without a safe boundary or clear result. Compare actual skill instructions, agent handoffs and existing automations; extend an owner or compose existing capabilities when that covers the outcome. Do not clone a generic skill merely because one project's history exposed the need.

When the candidate concerns prompts, agents or orchestration, inspect representative traces and the actual configured model/effort. Check outcome, acceptance, evidence, authority, tool routing, required output and stop rules. Prefer surgical edits that remove repeated process, stale scaffolding, irrelevant tools or contradictions. Give conditional references a clear trigger and purpose; retain permission and environment guards. Change one prompt group, model or effort at a time against the same representative cases. Compare correctness and completeness before total calls, turns, retries, tokens, latency, cost, duplicated evidence and waiting without new signal. Model choice cannot replace missing acceptance, dependency or validation rules.

For long workflows, separate productive build/verification from coordination and promotion lead time. Investigate repeated unchanged polling, stale reasoning, redundant agents, rereads, gates without named risk, aborted goals, repeated task fingerprints or terminal events, unnecessary full-history forks, and prepared artifacts that never reach an authorized promotion. Treat these as regressions only when traces show harm; duration or timeout ratio alone is insufficient. Do not conceal confirmed failures behind green tests. Also check false-positive routing: keyword-only skill selection, unrelated governance leading the answer, branch commentary used to justify read-only work, or GUI use when a reliable CLI, API, MCP, log or specialized browser answers the question. Test proposed changes against the original request and contradictory cases; lead the resulting response with the requested outcome.

Choose a skill for stable procedural knowledge; a custom agent for bounded specialist work with a distinct handoff; an automation for a verified cadence/event, stable destination, unambiguous prompt and safe authority; an extension when an owner exists; or skip if covered, one-off, unclear, broad, unsafe or under-evidenced. Do not invent a schedule or role. For a high-confidence new asset, keep the trigger narrow, separate read-only from mutation, state source freshness and stop evidence, and preserve user files and plugin caches. For a new skill, add concise `agents/openai.yaml` display name, description and `$skill-name` default prompt; validate frontmatter, references, script shell syntax and a safe representative dry run. If the standard validator is unavailable, perform equivalent checks and disclose that limit. Do not claim activation until files or external state are verified.

Present the decision before creation details in a short table with **Repeated workflow**, **Evidence and dates**, **Frequency/confidence**, **Form** and **Decision**. Include enough evidence to distinguish occurrences. Close with created or extended paths and validation, covered/unsuitable skips, candidates needing evidence, automation and agent decisions, and any reliance on unverified memory. Keep the report proportional to the findings.
