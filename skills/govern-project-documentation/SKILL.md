# Govern Project Documentation

Treat documentation as a versioned operating contract. Determine where durable knowledge belongs and verify relationships between sources; this skill does not own product requirements or add a documentation phase to normal delivery. Read the nearest instructions and only sources needed for the current question. Reuse the baseline unless topology, authority, canonical paths or relevant content changed.

An audit, review or recommendation is read-only. Create, move, delete, scaffold, rewrite contracts, initialize Git or split repositories only within an authorized implementation. Preserve dirty worktrees and unrelated changes. Publishing, deployment, branch protection changes and moving sensitive sources need their own authority. An unversioned parent directory is not normative merely because it groups repos. Incidental drift during product or operational work activates this skill only if it affects authority, scope, required evidence or progress; otherwise keep it subordinate to that work. Match the requested outcome, not words such as “audit” or “documentation.”

Choose the smallest useful depth: a targeted path/contract check; topology and ownership across repos; requirement-to-change-to-release traceability; or authorized scaffolding/normalization. Run `bash scripts/audit_workspace.sh /absolute/workspace/path` for topology, a first full governance audit, or a possibly changed repository layout. Reuse its result and verify only changed dimensions at closeout.

Classify ownership by Git and deployment reality: a single repo has one codebase, a monorepo has several codebases under one Git root, and a multi-repo product has independently versioned repos. Several folders alone do not make a multi-repo product. Keep transverse and technical docs together in a single repo; place transverse truth at the monorepo root and subtree detail nearby; for multi-repo products use a versioned governance home for business/product/system truth and technical repos for internal architecture, tests, deploys and runbooks. Preserve established conventions unless migration has a real purpose. Read [governance standard](references/governance-standard.md) when selecting canonical allocation or traceability structure; read [usage workflow](references/usage-workflow.md) when asked to install, operate, test or roll out this skill.

Identify one canonical path per relevant concern: current state, rules, requirements, architecture/ADRs, design, roadmap, findings, operations and releases. Report evidenced problems such as duplicated mutable state, stale adapters, broken links, normative docs outside Git, unlabeled As-Is/To-Be, sensitive inputs without policy or external sources without owner/version. Keep operational systems distinct from initiative states: discovery, design, approved, implementation, staging, production, blocked, superseded and cancelled. A proposed design is not deployed behavior.

Instruction precedence is current user instruction, nearest `AGENTS.md`, broader project/governance `AGENTS.md`, non-conflicting adapters such as `CLAUDE.md`, canonical topic document, then history. Apply immaterial lower-priority conflicts silently; for material conflicts identify the exact affected contract. Distinguish proposed, accepted, implemented, verified and deployed. Preserve source statements and mark superseded decisions. Update the existing canonical spec rather than creating `SPEC.md` by default. Keep mutable product state out of agent instructions; infrastructure records stable non-secret identity and procedures separately from observed SHA, deployment and incidents.

A technical repo that operates independently should document its role, governance location, Gitflow, environment limits, tests and fallback if governance is unavailable. Design references retain accepted assets/components, allowed delta and source-to-build lineage. For design ownership or traceability, use [design continuity](../dautia-project-cycle/references/continuity.md#documentar-el-diseno); ordinary design updates stay with the implementer and reviewer.

Where formal traceability is required, use stable IDs through business rule → requirement → decision/increment → PR or commit → test → environment → release or explicit no-release reason. Planned work can stop at source, decision, acceptance and future increment; small routine updates need no full matrix or premature release evidence.

For authorized scaffolding, use `assets/templates/`, replace placeholders, migrate one source-of-truth concern at a time, preserve or mark history as superseded, and update links and local contracts. Do not place governance templates in an unversioned workspace folder. Verify affected normative paths, links and obsolete names; run `git diff --check` and inspect branch/status in changed repos. Broader link checks, manifest validators, recursive audits, CI or provider checks apply only when the affected boundary requires them.

Return a compact verdict with evidence, the topology/document-home decision when relevant, prioritized findings, changed paths, validation, Git state and residual risk. Do not create documents or rerun audits solely for a reporting format.
